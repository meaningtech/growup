# Growup development instructions

- Growup is isolated from Solaraf. Do not import runtime files or domain code from `../solaraf`.
- Keep code, tests, documentation, comments, and commits in English.
- Never expose credentials in source, logs, test fixtures, screenshots, or exports.
- When sending a Growup screenshot through Grog on Telegram, verify that the local file is a valid image and use `grog telegram-send-image <absolute-image-path> [caption]`, which calls Telegram `sendPhoto`. Never pass an image path to `grog send --telegram`: the generic sender reads files as text and will send the PNG contents or path instead of a photo.
- All environmental, botanical, price, and cost values shown to users require a source, observation date or version, and confidence level.
- Unknown provider values remain unknown. Do not silently replace them with invented defaults.
- Backend and API behavior requires integration tests.
- Production code uses static imports only.
- Runtime-test behavior changes before committing or pushing.
- If the user says `vai`, `pusha`, `pushalo` or `pubblica`, do it immediately. Do not ask for confirmation, do not offer a later step, and do not wait. For Growup that means finish the current work, then commit, push `main`, deploy Cloud Run service `growup` in `europe-west1`, and shift 100% traffic to the new revision.

## Current architecture

- `src/` is the React/Vite map-first client. `server/` is the Express API. Shared domain contracts live in `src/types.ts`; deterministic calculation code lives in `src/lib/`.
- PostGIS is authoritative only for boundary, exclusion, path and protected-tree geometry validation/measurement. Do not store project documents in PostGIS.
- Project persistence reuses the explicitly configured Firestore Enterprise Mongo-compatible database path `/solaraf` as infrastructure only. Runtime code must pass the host/database guard in `server/mongo.ts`; do not create another database or Mongo user.
- `scripts/migrateBrandCollections.ts` is the one-way, idempotent Growaf-to-Growup collection migration. It must validate READY `_id` indexes before scanning and must never delete or rewrite the immutable legacy source collections.
- Growup owns only `growup_users`, `growup_projects`, `growup_project_revisions` and `growup_calculation_runs`. Preserve owner isolation and every READY index: unique document `_id` indexes, sparse unique user email, `{ ownerUserId: 1, updatedAt: -1 }` for projects, `{ ownerUserId: 1, projectId: 1, revision: -1 }` for revisions and `{ ownerUserId: 1, projectId: 1, createdAt: -1 }` for calculation runs.
- Google sign-in is optional. Anonymous users can analyse and design. Saving, reopening and exporting stored projects require a verified Google ID token and the signed HttpOnly `growup_session` cookie.
- Public project access uses signed, expiring HMAC tokens containing only project ID, share-version and expiry. Public reads use the indexed project `_id`; review mutations remain bounded, append immutable project revisions and must fail immediately after owner revocation or token rotation.
- The AI assistant is provider-agnostic through an OpenAI-compatible server adapter. Keep provider keys server-only, resolve proposed species against the curated catalogue, validate every action, and require user confirmation before mutation. Provider calls use bounded configurable timeouts and may retry network failures, timeouts, HTTP 429, HTTP 5xx and empty or malformed structured output; other HTTP 4xx responses fail immediately. DeepSeek structured-output requests disable thinking and provide at least 2,500 output tokens; after an empty/malformed JSON-mode response, the bounded retry omits `response_format`, requests one compact JSON object and still schema-validates any plain or fenced object extracted from the answer. The separate formal-review route uses a stricter evidence-bound audit prompt and validated report schema; it must never reuse the mutation-oriented assistant response as a project certification. Its compact context must retain site-constraint counts, evidence provenance, irrigation/economic configuration, network readiness and cost breakdowns so the model can audit cross-section coherence without receiving unnecessary geometry payloads.
- `server/economics.ts` resolves one global USD planning basket through a live country-to-currency mapping and USD exchange table. Never add country-specific pricing branches; local rates are explicit user overrides. Conversion remains an internal estimate and must not be exposed as UI or report mechanics.
- `server/export.ts` is the only project export composer. GeoJSON and CSV output must remain deterministic for the same stored project and include calculation/model metadata without credentials or private identity data.
- The production container is a two-stage Node 20 image. Cloud Run injects PostGIS, Mongo, Maps, OAuth, AI and session credentials through environment variables or Secret Manager; no deployment secret belongs in the image.
- API responses enforce an exact production-origin CORS allowlist, browser security headers and per-instance IP rate limits. Keep assistant, authentication and provider/compute budgets independently configurable; expensive geocoding, PostGIS, evidence, economics, recommendation, layout, irrigation and cost routes must remain protected.
- Place search and reverse geocoding use Nominatim first and the server-side Google Maps Geocoding API as a credential-protected fallback. Provider keys never enter response data or evidence URLs; coordinates remain the explicit last-resort location when both providers fail.
- Site evidence combines Open-Meteo historical weather, ISRIC SoilGrids WCS, Sentinel observations, the ISRIC/Shangguan global depth-to-bedrock raster, BGR/UNESCO WHYMAP groundwater context and the existing terrain/land-cover providers. The client presents overview, wind, soil, subsurface, satellite and source-traceability tabs; every source entry must explain the data read, Growup calculation and affected planning decision.
- `src/lib/fireOperations.ts` targets the EFFIS 2.0 WMTS service, layer `ecmwf.fwi`, matrix `ECMWF3857`, using the field-centroid tile at the service maximum zoom 6 (1024 px). The former `/effis` WMS and v1 current-situation viewer are decommissioned; do not restore those URLs without a new live response check.
- Production runs as Cloud Run service `growup` in `europe-west1` with the dedicated `growup-runtime` service account and `growup-*` secrets. It intentionally mounts the existing Cloud SQL instance whose immutable technical resource name is `growaf-postgis`; do not duplicate or rename that data service during brand changes.
- The canonical public origin is `https://growup.earth`. Keep browser-key referrers and the Google OAuth authorized JavaScript origin aligned with it; Cloud Run-generated hostnames are operational endpoints only.

## Domain invariants

- `DesignConfiguration.objectives` controls suitability weights, species ordering and layout composition targets. `DesignConfiguration.speciesMix` persists normalized target percentages and optional succession overrides; the deterministic layout engine allocates against those targets while preserving spacing and hard site constraints. Normalize every untrusted configuration before use.
- The internal `species` workflow section is presented as Planning/Progetta and contains Species, Firebreak and Work equipment subtabs; the following `layout` step is Design/Piano. Keep both internal identifiers stable for persisted projects and onboarding; subtab changes must not reset `DesignConfiguration`, and mobile workflow labels must stay inside their navigation buttons. Fire/Incendi is a normal `WorkspaceSection` between Water/Acqua and Costs/Costi; Analysis/Analisi follows Costs; Care/Cura follows Analysis; Harvest/Resa is the final step after Care. All participate in previous/next and assistant navigation and must never reopen as modals or backdrops. Populated Evidence and Fire inspectors retain persistent footer actions to Planning and Costs respectively. The Care inspector is a handbook plus calendar built from the selected layout; it is not the Fire operations checklist. Harvest estimates per-tree kg and farm-gate value from a curated catalogue (olive oil, carob, wine included); it must not apply FAO t/ha to mixed layouts, and species without a record stay unknown.
- `LayoutVariant.composition` records actual stratum/succession counts plus productive, native and nitrogen-fixer shares and their targets.
- Species with `invasiveStatus: blocked` never enter a layout. `monitor` species can never be rated `recommended`. Missing critical soil pH caps a result at `conditional`.
- The 51 design-ready species are a curated planning catalogue, not satellite-derived observations. Switchboard and GlobUNT support taxonomy/catalogue linkage; climate, rainfall, soil and management envelopes remain explicit planning estimates with linked source groups. Automatic palettes must exclude any species with a poor climate or water component, and drought-tolerance scores must never mask annual rainfall below the supported envelope. Keep unknown jurisdiction-level native range explicitly unverified.
- Every layout is deterministic for the same normalized site, species, configuration and seed. Existing woody Sentinel polygons, field-observed trees, exclusions, paths and setbacks are hard placement constraints.
- `LayoutVariant.generation` records the layout engine version, seed, full/partial mode, locked-tree count, assumptions and conflicts. Partial regeneration must preserve every valid locked tree byte-for-byte and reflow only unlocked candidates.
- The Design/Piano inspector is divided into Summary/Sintesi, Plants/Piante, Sun/Sole and Edit/Modifica tabs. Generation metadata remains persisted for reproducibility but must not be rendered as a technical audit card. Keep source-backed values and operational controls; avoid introductory copy that repeats what the data already states.
- `LayoutVariant.machinery` records exact corridor centre lines, required widths, turning areas, one continuous drivable perimeter loop per parcel component, connected serpentine manoeuvre routes and clearance results. Route geometry must remain inside the parcel, clear mapped obstacles at the configured operating width, feed protected irrigation-crossing calculations and export deterministically. Planned trees, machinery, irrigation, boundary, constraints, infrastructure and evidence overlays are independently switchable map layers.
- Manual service-path drawing is not exposed in the map toolbar or site tools. Preserve imported paths as hard placement constraints and keep their width/removal controls, while machinery perimeter loops and manoeuvre routes remain generated automatically. Existing woody vegetation stays available as a switchable layer without a permanent in-map legend.
- Machinery-space reservation is opt-in. `DEFAULT_MACHINERY_CONFIGURATION.enabled` and normalization of omitted machinery input must remain `false`; only an explicit user action may reserve corridors and turning headlands.
- Firebreak reservation is opt-in. `DesignConfiguration.firebreak` stores the adjacent fuel model, expected flame length, planned width, treatment, vehicle-access intent and protected-pipe-crossing intent. `LayoutVariant.firebreak` must map a continuous inward perimeter reserve, exclude every planned tree from its width, identify windward sections from the same historical wind profile, retain its evidence and local-review requirement, and export deterministic `firebreak` GeoJSON features. The 2.5× flame-length value is a planning basis, never a safety certification or substitute for the competent local AIB authority.
- `src/lib/fireRisk.ts` produces a deterministic planning-attention screening from historical dryness, wind, terrain, observed woody cover, the selected fuel assumption and the mapped firebreak response. It is never an EFFIS class, ignition probability or spread model. Fire/Incendi must open on Analysis and expose Data and Sources before the secondary Operations checklist; never let checklist cards dominate the default page.
- `ProjectState.fireOperations` persists the EFFIS `ecmwf.fwi` WMTS forecast snapshot, its 8 km resolution, checklist status, inspection dates and notes. The overlay is operational context rather than parcel-scale fire certification; preserve the provider, forecast date and source link in the UI, revisions and exports.
- `ProjectState.analysis` persists the latest validated `ProjectAnalysisReport` for anonymous recovery and authenticated revisions. `src/lib/projectAnalysis.ts` fingerprints all review inputs; preserve stale reports for traceability, mark them stale when the fingerprint differs, and require a rerun before relying on the verdict. Formal review covers evidence, species, design, water, fire, operations, economics and cross-project coherence, cites concrete fields/sources and explicitly separates modelled data, deterministic outputs, assumptions and unknowns. Finding dispositions (`resolved` or `accepted`) are explicit user decisions stored on the report and may be reopened; they do not silently recalculate the AI verdict. Agent remediation is one explicitly started run over selected open findings: it applies only server-validated project actions, regenerates dependent layouts/calculations, reruns the formal review after every cycle, persists score/step history on the latest report, and stops after resolution, repeated actions, two non-improving reviews, a four-cycle cap, user cancellation or failure. A stale report must not make the Agent start control inert: explicit start first refreshes the formal review and reconciles the selected open findings before applying changes. It never opens the assistant chat and must never claim to complete field checks, permits, missing evidence or physical work.
- Formal-review evidence references remain internal traceability metadata. Never render raw object paths, collection fields or database-shaped references in the user interface; findings expose only their localized dimension, severity and natural-language title, explanation and recommendation.
- `ProjectState.collaboration` persists bounded review comments, the current review decision and the revocable share configuration. Public share endpoints return the server-built `SharedProjectState`; never expose `share.tokenVersion` or the internal formal AI `analysis`, accept more than 200 comments, or let a view-only link mutate state. A shared plan includes the remaining non-secret project dossier and an interactive map with independently switchable planning/evidence layers. `share.includeCosts` controls disclosure of the cost plan: when false, redact the economic configuration, cost plan and every monetary irrigation field while preserving non-monetary irrigation geometry, quantities, hydraulics and operating data. The shared section navigation excludes Analysis, uses a three-column colored grid, and keeps review comments and decisions separate from the internal AI report. Reuse the stored project data for shared climate/water charts, seasonal wind climatology and interactive hourly plant-solar exposure; the shared solar control must operate the same map layer instead of presenting a disconnected visualization.
- Owner share controls expose the generated URL as a selectable anchor that opens in a new tab with `noopener noreferrer`, alongside a separate clipboard button with visible success feedback and a browser fallback. Keep both the project-library read-only dialog and the collaboration panel on this shared control, and prevent URL overflow on mobile. The shared evidence register must aggregate base evidence, soil properties and vertical layers, satellite soil screening, bedrock, groundwater, Sentinel and existing-vegetation evidence without discarding richer temporal fields when duplicate provider records are merged.
- Advanced layout editing applies only to the selected variant and validates every resulting coordinate against site restrictions. Multi-selection itself is ephemeral UI state; replacements, locks, deletions, bearing alignment and equal spacing are persisted as variant tree edits through the normal project save/revision path.
- Protected irrigation crossings must include both machinery corridors and enabled firebreaks. Preserve their sleeves in network components, procurement quantities, exports and operational schedules.
- Project schema version 4 requires normalized `fireOperations`, `collaboration` and `operations` fields. Missing `operations` remains `null`. Every authenticated save appends an immutable project revision and, when calculated results exist, an immutable calculation run. Use optimistic revision checks; never overwrite revision history or embed an unbounded history array in the current project document.
- Project-state changes auto-save after a 1.2-second debounce. Anonymous work writes the recoverable browser draft; authenticated work also queues the owner-isolated server save and immutable revision. Manual Save is an explicit checkpoint and sign-in entry point, not a requirement after each edit.
- Authenticated projects use a full-page searchable Active/Archived library. Archiving changes reversible project metadata without deleting the current document or immutable revisions. The per-project Share action creates only signed, revocable, expiring `view` links; read-only recipients must never gain comment, review, save or mutation controls.
- First-run onboarding is skippable and resumable. Keep `{ status, step, updatedAt, projectName? }` in `growup:onboarding:v1`; authenticated users sync the newest timestamp into `growup_users.preferences.onboarding` through `PUT /api/user/preferences/onboarding`. Accepted steps are `welcome`, `location`, `boundary`, `analysis`, `species`, `design`, `water`, `fire`, `costs`, `review`, `care`, `harvest`, and `complete`; accepted statuses are `active`, `skipped`, and `completed`. The tour must guide every real workspace step rather than simulating a separate workflow.
- The onboarding location step must remain blocked until the user selects an explicit geocoded result or enters valid coordinates and the live map reaches parcel scale (zoom 12 or closer). Typed but unselected place text and the global initial viewport are never sufficient.
- Site-profile overrides require a value, reason, source label, observation date and immutable audit entry; recalculated suitability must consume the overridden profile rather than mutating provider evidence.
- Out-of-bound access, water-source, existing-tree and irrigation edit attempts are non-destructive: preserve the last valid geometry, keep point-placement mode active for an immediate retry and show temporary actionable guidance instead of a persistent blocking error. Persisted invalid project geometry must still identify the affected feature class and block downstream calculations until corrected.
- `SiteProfile.soil.properties` retains modelled chemical, physical and derived estimates with source, depth, units and optional 90% prediction intervals. SoilGrids values are parcel-scale screening, not laboratory measurements: do not present total nitrogen as plant-available nitrogen, infer unprovided phosphorus/potassium/micronutrients/salinity/contaminants, or convert Sentinel bare-soil variability into chemistry without local calibration.
- `SiteProfile.soil.verticalProfile` retains the six standard SoilGrids layers from 0–5 cm through 100–200 cm. `SiteProfile.soil.depthToBedrock` retains field-clipped 250 m model-cell samples, their bounds, median and sampled range; it is modelled bedrock depth, never measured effective rooting depth. `SiteProfile.groundwater` retains WHYMAP regional aquifer type and recharge class only; it must never be presented as parcel water-table depth, well viability, water quality, abstraction rights or seasonal supply.
- `Evidence.observedAt` remains the legacy compatibility timestamp. New evidence must populate every temporal field actually known—`dataObservedAt`, `coverageStart`, `coverageEnd`, `publishedAt`, `retrievedAt` and `computedAt`—without manufacturing precision. The Evidence UI and shared read-only dossier must render these dates with distinct labels instead of collapsing acquisition, publication, retrieval and calculation into one date.
- Google Maps remains the browser map engine. The layer panel can compare the native Google satellite basemap with Esri World Imagery, overlay the latest field-clipped Sentinel true-colour scene, render sampled depth-to-bedrock cells and display WHYMAP regional groundwater context. Keep the providers independently switchable, expose opacity where layers overlap and retain visible provider attribution; never imply that the optional comparison layer is newer unless its acquisition date is known.
- `SolarResourceProfile.windClimatology` contains annual and meteorological-season summaries with eight source-direction sectors, mean 10 m speed, hourly-speed P90, calm frequency and sample counts. Directions always mean where wind comes from; P90 is not a gust estimate. Keep the wind rose, seasonal selector, map vector, windbreak orientation and firebreak windward priority tied to this single source profile, and retain the warning that reanalysis cannot resolve local obstacles or gust corridors.
- `src/lib/solarExposure.ts` derives the representative daily plant-exposure view from Open-Meteo UTC hourly climatology, NOAA solar geometry and the versioned species growth model at the visible succession year. Keep local-solar-hour conversion, direct/diffuse radiation, individual crown-shadow intersection and map overlays deterministic. Always show provider, period/version and confidence, and state that local horizon, off-site obstacles, pruning, leaf density and crop PAR require field verification.
- `GrowthState` exposes deterministic low/base/high height and crown estimates plus model version, hierarchy and confidence. Zero values outside the active planting/removal interval are intentional.
- Planned trees use stable row/sequence identities derived from persisted `rowIndex` and `positionIndex` (`A1`…`Z1`, `AA1`…), plus the first two localized species letters on map markers. Preserve the same `plantCode` in selection UI, GeoJSON and CSV exports. Hovering a crown/marker and tapping or clicking it must expose a real in-map detail card with the code, localized common name, scientific name, row and sequence; tap/click selection persists until explicitly closed and remains unobscured above the mobile timeline and map toolbar.
- `LayoutVariant.metrics.densityBasisAreaM2` is the net plantable area used for `treesPerHectare`. Always expose the count and denominator alongside density, and recalculate density, canopy, crop-interior and species-count metrics after manual tree additions, replacements or deletions and when hydrating legacy saved projects.
- `IrrigationConfiguration` includes source, flow, pressure, emitter, distribution-efficiency, operating-window and manual line-override inputs. `IrrigationNetworkPlan` must preserve source placement, editable geometry, obstacle routing, head/flow checks, measured versus purchase pipe quantities and the component bill of materials. An unroutable segment remains editable but must be marked blocked, rendered as a conflict and keep procurement explicitly non-ready; never fall back to a direct line through a protected obstacle.
- The populated Water/Acqua inspector uses Summary/Sintesi, Setup/Fonte, Network/Rete and Checks/Verifica tabs. The populated Costs/Costi inspector uses Summary/Sintesi, Setup/Impianto, Management/Gestione and Rates/Tariffe tabs. Keep the primary action outside the tab panel, expose issue counts on the relevant tab, and leave only tabs with meaningful pre-calculation content enabled.
- Economic values use `EconomicConfiguration.baseCurrencyCode = USD` internally; present only the project's resolved local planning currency and user-editable local rates. `plantUnitCostOverrides` stores bounded per-species unit prices and must flow through establishment costs and exports without mutating catalogue reference prices. Syntropic operating curves may decline with succession, while establishment CAPEX remains a historical total.
- `src/lib/operations.ts` builds a deterministic planting handbook and care calendar from the selected layout. The local operations database is `data/operations/IT.json`, seeded from `data/operations/curated-IT.json` by `npm run data:operations` until every design-ready species is complete. Records match on scientific name, then a country climate group (Mediterranean, temperate or tropical), then genus/archetype fallbacks. Unknown fields stay unknown. Site climate shifts windows. PFAF text and raw PEP725 observations are not ingested. The printable operational schedule opens from Care/Cura, not Costs. `ProjectOperationsPlan.plantingDate` is the user-chosen origin of the calendar; later work is dated from that day. Care shows a month grid with moon phases. Task how-to and species notes open in a small modal. Inspection is not a calendar procedure. Waning-moon pruning is an optional traditional cue with low confidence, never a measured sap-flow model.
- Routine woody-system maintenance is calculated by `src/lib/maintenance.ts` and versioned independently. Preserve task-level hours for vegetation control, pruning, biomass/succession management and inspection/replanting; scale them by managed area, active plants and fixed mobilisation, then apply the project labour rate. Syntropic routine workload reaches the explicit zero-hour forest-autonomy endpoint in year 25; harvest, optional productive management and extraordinary work remain excluded. Monoculture reaches a recurring mature-orchard plateau, and every estimate must retain its source basis, confidence and exclusions.
- Maintenance results are part of `IrrigationEstimate.systemMaintenance` and every cost-timeline row. Keep the same versioned task breakdown in calculation snapshots, assistant context, GeoJSON/CSV exports and printable operational schedules; annual OPEX must include this labour exactly once.
- Printable operational schedules must derive plant counts, labour, irrigation procurement, monthly demand, machinery reserves and evidence records from the selected generated design; never introduce placeholder quantities. Print mode must remove the application grid, preserve full-width A4 flow, keep planting rows together, start the evidence register on a fresh page and produce no clipped, empty or horizontally overflowing pages.
- Sentinel-1 output is a same-orbit backscatter anomaly, not volumetric soil moisture. Keep this distinction in UI, API and exports.
- Mobile map controls use a single-row bottom dock above any timeline; coach panels and toasts remain above the safe-area bottom navigation, interactive form controls render at 16 px or larger to prevent iOS focus zoom, and the desktop map/inspector split collapses without horizontal overflow at 820 px and below. The ten-step mobile workflow rail uses 16 px icons, compact labels and a 54 px base height plus safe-area inset; every localized label must remain inside its equal-width button at 320 px. Care/Cura and Yield/Resa stay short labels.
- Primary workflow actions live in a persistent inspector action bar on populated Site, Planning, Design, Water, Costs and Care panels. Keep the content independently scrollable and reserve separate space for the action, toast, succession timeline and mobile workflow navigation; no layer may cover another.
- On mobile, the inspector flow header remains in normal document flow directly below the map. It must not use sticky positioning: the guide must touch the map edge, the panel body must start below the guide, and the first title must never overlap it. `e2e/responsive-accessibility.spec.ts` enforces these geometry invariants at a 390×844 viewport.
- The compact top bar keeps the icon-only assistant trigger, authenticated project trigger and hamburger at the far right. Ask/Chiedi and Projects/Progetti remain icon-only at every viewport with localized accessible names and titles. The signed-in account trigger is one circular surface: the profile image or fallback initial fills the control and must never appear as a separate round element nested inside a square button. The product menu must not duplicate the avatar; its authenticated footer is a plain Sign out/Esci action with the user name as secondary context. On phones, the initial assistant composer stays at most 140 px tall, keeps at least 8 px clear of workflow navigation, uses a short non-example placeholder and expands only for availability notices, processing, errors or proposals. Authenticated project selection lives in its own spacious full-screen mobile page (wide dialog on desktop), never in the product menu. Language, tour, information, save state/actions, revision history, exports and authentication belong in the right-aligned product menu. On mobile, the succession-year control is anchored inside the map above its toolbar and scrolls away with the map; it must never remain fixed over inspector content. The page root must remain locked against horizontal scrolling and Safari lateral overscroll.
- Public metadata uses `https://growup.earth/` as the canonical URL and `GrowUp - Data driven agroforestry planning` as the public title. Keep Open Graph/Twitter metadata, `public/growup-social-card-v2.jpg` at 1200×630 and below 500 KB, PNG browser/touch icons, `site.webmanifest`, `robots.txt`, `sitemap.xml`, and `llms.txt` aligned whenever the public product description changes. Social-card responses must keep `Cross-Origin-Resource-Policy: cross-origin` so external preview renderers can embed them; all other resources remain `same-origin`. Product information must remain behind the explicit Info control in the interactive UI while the static crawler fallback keeps equivalent indexable copy. The Info panel must identify GrowUp as open source and link to the canonical repository at `https://github.com/meaningtech/growup`.
- Repository presentation is part of the product surface: `README.md` links the live application and case study, documents the architecture and evidence boundaries, and embeds production screenshots from `docs/images/`. Regenerate those images with `GROWUP_SCREENSHOT_URL=https://growup.earth npm run docs:screenshots`; the script imports only the explicit equatorial test fixture and must never capture private user data. Keep the MIT license, contribution guide, security policy, code of conduct and GitHub issue/PR templates available and consistent with meaningtech ownership.

## Verification

- Baseline: `npm run typecheck`, `npm test`, `npm run build`, `npm run test:e2e`.
- `GROWUP_BROWSER_CHANNEL=chrome` selects installed Chrome for local Playwright runs when the bundled headless shell is unavailable; leaving it unset preserves the standard CI browser.
- `.github/workflows/verify.yml` is the required pull-request and main-branch gate: typecheck, unit/integration tests, production build and the credential-free browser acceptance subset must remain green.
- The deployed acceptance workflow is `GROWUP_BASE_URL=<cloud-run-url> npm run test:acceptance`; it must exercise live evidence, layout, hydraulics, economics and perimeter planting against one explicit imported field.
- Property and performance gates live in `src/lib/layout.property.test.ts` and `server/performance.test.ts`; do not weaken plantability, determinism, catalogue, growth or layout thresholds to hide regressions.
- Live Mongo: set `GROWUP_LIVE_MONGO_TEST=1` with the guarded existing `MONGODB_URI` and `AUTH_SESSION_SECRET`, then run `npx vitest run server/mongo.live.integration.test.ts`.
- Browser behavior must be verified with explicit imported field fixtures; production must never bundle or auto-load a localized default field. Keep screenshots and generated test artifacts out of Git.
- `e2e/firebreak.spec.ts` is the browser contract for soil evidence, wind visualization, source traceability and firebreak configuration/enforcement. Keep its wind-layer toggle, seasonal rose, windward-priority and no-plant assertions intact when these schemas evolve.
- `e2e/operations-collaboration.spec.ts` is the browser contract for the analysis-first fire page, secondary fire operations, formal AI review persistence, bulk tree editing, authenticated sharing, public comments/review and local recovery.
- `e2e/assistant-live.spec.ts` is the opt-in deployed-provider contract: it must complete a real evidence/design/calculation flow, validate and apply an assistant proposal, then obtain an eight-dimension formal review without API mocks.
